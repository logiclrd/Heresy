# Script Instrument rework — exploratory design plan

**Status (2026-11-22): Proposal / discovery only. No implementation has been approved for the model or editor.** The canonical open task is [the Instrument rework TODO](todo.md); the separately scoped Pattern/Sequence allocation-relaxation task is [issue #58](https://github.com/logiclrd/Heresy/issues/58). Do not interpret this document as the current Script Instrument API.

## Existing problem and scope

Today `InstrumentDefinition` (Data Instrument) and `ScriptInstrumentDefinition` are separate types. A Script Instrument uses three independent restricted expressions: `Source` chooses an index into its manually authored tone specifications, `PitchExpression` adjusts pitch, and `NnaExpression` chooses the note's NNA behavior. Tone creation is inconvenient and does not provide the desired general procedural way to generate/configure an Instrument's output. The common tone-grid/model decision and the procedural program decision should be explored separately before considering unification.

The future design should investigate **broader procedural control of the resulting/generated Instrument sound or tone object** instead of assuming an indexed selector is the only surface. Compare: selecting existing reusable tone data, constructing/deriving a per-note tone or sound description, and configuring controlled output properties. Preserve existing sound-dependency discovery, source remapping/import, deep duplication, NNA/filter/envelope semantics and snapshot isolation. Do not promise arbitrary mutable renderer/graph access without a safety and lifetime design.

## Proposed two-phase program model (owner requirements)

Explore one script program with **an initialization/setup block** followed by **a per-note handler**.

- **Initialization block:** called on a deliberately chosen lifecycle (to be designed, e.g. once per compiled instance or prepared playback generation), on a *non-realtime* worker before processing notes. It can prepare lookup tables, derived specifications, caches and other state **reused by multiple note-handler invocations**. Allocations here are **allowed without an allocation warning**. Clearly specify when it is rerun after source edits, new playback snapshots, live revisions or offline export, who owns the objects, and when they are disposed.
- **Per-note handler:** called for incoming note/pitch context and returns or configures the supported generated tone/sound. It may **read/reuse** initialization data and may **allocate managed objects**, but any such allocation should elicit a **nonblocking advisory warning**, not an error solely because allocation occurred. The warning should explain the note-frequency/performance implication and help move reusable work into initialization. Decide how to identify allocations (syntax, semantic analysis, supported helper calls and indirect allocation) without falsely claiming complete detection.
- **Current Script Instrument behavior is unchanged.** The existing three expression programs do *not* gain this initialization block or warning scheme until the rework is designed and implemented. Do not project these proposed semantics onto current expression evaluations.
- **Ownership and threading:** keep generated data scoped to a frozen publication/generation; avoid modifying authoring objects on the PCM/device callback, sharing unsynchronized mutable state between simultaneous notes/generations, or retaining stale source/sound references. The design must specify thread affinity and initialization/teardown for simultaneous offline render, preview and normal transport.
- **Hot-path policy:** the internal engine should strictly avoid *new* managed allocations in code paths that systematically execute more than approximately **100 times per musical row**, and should generally *try* to avoid allocations in cooler paths. This is an engineering classification guideline, not a magical warning threshold or a quota checked against all user code. A bounded per-note object allocation can be tolerable and warn-only **even if an especially dense script runs many notes**; protect real-time stability with resource and workload limits independent of whether the diagnostic is an error.

## Open decisions for the design review

1. **Type and editor:** same Instrument object with optional front-end program, shared tone editor/model, or two types with fully shared underlying tone model and common UI? Preserve existing song compatibility and field migration.
2. **Generated object interface:** what exactly can code select, instantiate, modify or return? Which properties are runtime-owned, clone-on-write or immutable? Can a note produce a derived tone without exposing unbounded graph mutation?
3. **Initialization lifetime:** how many program instances exist for a song/render/voice, when is setup executed, what happens if it throws, how are generated buffers and other resources disposed, and how are deterministic seeds handled?
4. **Allocation advisories:** define static analysis and warning severity/location; no warnings for the setup block, advisory for possibly allocating operations in the per-note handler. Avoid presenting the absence of a warning as proof that there are zero allocations. Discourage repeated allocation in loops and expose compiler diagnostics without blocking valid author code merely for allocating.
5. **Safety and performance:** compile/prepare away from the realtime callback, quantify work/CPU budgets and resource limits, account for polyphony and multiple generations, and test typical and adversarial allocator behavior alongside PCM parity.
6. **Dependency/snapshot compatibility:** make static sound dependency discovery, source references/import/remapping, deep duplication, persistence/migration, compilation errors and existing Instrument tone/NNA/filter/envelope semantics explicit.
7. **Help and acceptance:** reference text must describe only the implemented runtime API; test reuse of prepared initialization data across notes, allowed setup allocations without warning, permitted per-note allocations with advisory, compilation/revision isolation, teardown and ordinary audio behavior. Plan practical physical acceptance of the pitch helpers already exposed to existing Script Instruments once tone authoring is usable.

The Instrument rework remains separate from [PR #50 F6 source-call provenance](https://github.com/logiclrd/Heresy/pull/50) and from [issue #58](https://github.com/logiclrd/Heresy/issues/58), which concerns relaxation of current **Pattern/Sequence** restricted scripting. Neither should be blocked waiting for the Instrument redesign.
